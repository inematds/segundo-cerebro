🧭 Point the agent to the vault

Claude Code only uses what sees. If your second brain — the vault generated by Graphify—it’s tucked away in a corner of the disk that it never checks, so it’s as if it didn’t exist. The first step is always to put the vault inside (or next to) the project and tell the agent where it is, right at the start of the session.

🔰 New here? What are "vault" and the imports folder

O vault is the folder Obsidian's export produced: a .md by concept, with backlinks [[nome-do-no]], plus the GRAPH_REPORT.md. The course convention is to store it in a folder like graph-imports/<nome-do-grafo>/ inside the project, so it can be versioned and stays in the agent’s field of view.

It’s not enough for the vault to be on disk: the agent needs to be directed it before you start scanning the repository. The simplest way is an opening sentence that establishes the vault as primary source. The block below is a ready-to-paste prompt.

opening prompt (illustrative)

🎯 Objective: establish the vault as the source before asking any questions.

O segundo cérebro deste projeto está em graph-imports/<nome-do-grafo>/ .
Lá tem um .md por conceito (com backlinks [[...]]) e o GRAPH_REPORT.md
com os god nodes. Use ESSE vault como fonte primária antes de varrer o repo.

✔ How to verify: then ask "list the 5 god nodes in GRAPH_REPORT.md". If it responds with real names from the your graph, found the vault. If it invents generic names, the path is wrong.

⭐ Start with the god nodes

Where to start a question? With the god nodes — the most connected entities in the graph, listed in the GRAPH_REPORT.md. They are the hubs: entering through one of them brings the rest of the map along, because almost everything passes through there. Starting at a peripheral node is like entering through the back door.

🔰 New here? What is a "god node"

In the graph, each entity (node) has a number of connections. The god nodes are the most connected hubs — “Context Window,” “Hooks,” and “MCP” in a documentation set, for example. Graphify already calculates them and dumps them into the GRAPH_REPORT.md, together with suggested questions.

✓ Enter through a hub

  • ✓Covers more ground in one go.
  • ✓Brings the right neighbors along.
  • ✓The report already suggests where to go.

✗ Enter through an isolated node

  • ✗You see only an isolated piece.
  • ✗Takes many hops to get to what matters.
  • ✗Easy to stop before you find the context.

🔗 Let the agent follow backlinks

It came in through a god node—and now what? The trick is to let the agent follow the backlinks: the [[links]] that each note carries to neighboring concepts. Instead of stopping at the first node, it follows the neighborhood and builds an answer connected, not isolated.

That’s exactly what the vault is designed to allow: each .md points to the neighbors, so the agent navigates the meaning — not loose text positions. Visually, the path looks like this:

💬 Prompts that use the map

All of this becomes a habit with a prompt well put together. The difference between "explain X" and a prompt that points to the graph is huge: the second one tells the agent to enter through the hub, follow backlinks, cite the notes, and stay within the scope from the vault. The block below is this module’s main copy-run.

map prompt (illustrative)

🎯 Objective: answer from the map and cite the provenance, without scanning the repo.

Use o vault em graph-imports/<nome-do-grafo>/ para explicar <tema>.
Comece pelo god node mais ligado a ele, siga os backlinks [[...]] até os
conceitos vizinhos e cite cada nota .md que usar. Não varra o resto do repo.

✔ How to verify: the answer should cite note names from the vault (e.g.: Context-Window.md) and neighboring concepts—not a generic paragraph without a source. No citations = it didn’t use the map.

✓ Prompt that uses the map

  • ✓Points to the exact vault folder.
  • ✓Asks to start with the god node.
  • ✓Requires citing the notes (provenance).

✗ Vague prompt

  • ✗"Explain X"—without saying where to look.
  • ✗Let the agent scan in the dark.
  • ✗Answer with no source, hard to verify.

🛰️ Serve the graph via MCP (optional)

Reading Markdown files works — but Graphify can also serve the graph as tools programmatically, via MCP. Then the agent queries the graph precisely (a node’s neighbors, the shortest path) instead of relying only on the text. It’s optional, but powerful for large graphs.

🔰 New here? What is "MCP"

MCP (Model Context Protocol) is the standard that lets Claude Code call tools and read resources from an external server. Here, the server is the graph itself: it exposes functions such as query_graph that the agent calls when it responds.

start the MCP server (illustrative)

🎯 Objective: serve the graph as tools, not just as files.

# dentro do Claude Code (skill form):
/graphify . --mcp

# ou via terminal puro:
graphify --mcp

# tools expostas: query_graph · get_node · get_neighbors · shortest_path

✔ How to verify: ask "use query_graph to list the neighbors of <concept>". If it call the tool and return the linked nodes, the MCP is running. If it responds with text without invoking a tool, the server did not start.

🧪 Validate the answer against the source

Trust, but verify. The graph stores the provenance for each node—the source file the entity came from—inside the graph.json. When the agent makes a claim, you close the loop by tracing it from the concept to the source doc original and checking that it matches. It's the best defense against hallucination.

↑ The stated concept leads, through provenance of the graph.json, all the way to the original source doc, where you can check. The source docs don’t go into the vault: they stay in the project.

1

Capture the stated concept

Write down the response’s central claim and the node (note) that supports it.

2

Follow the provenance in graph.json

Each entity records which source file it came from. That’s the pointer to the evidence.

3

Open the source doc and check

If it matches, you can fully trust it. If it doesn't, it's a hallucination — correct the note or regenerate the graph.
